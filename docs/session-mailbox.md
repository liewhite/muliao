# 设计：会话信箱（取代「每条消息一轮」）

状态：已确认（2026-10-20）。确认后按「迁移步骤」实施，完成后并入 architecture.md 并删除本文。

## 1. 模型

每个会话是一个**信箱**加一个**消费者**：

- 一切要交给 agent 的东西都是往信箱里追加一条**信件**：用户消息（含附件）、对提问的回答、触发器事件、委派来的任务、后台任务的完成与检查、thread 交回的结果。按到达顺序排列。
- 消费者把信件喂给模型：信箱里有信件就开始一次**运行**，把还没处理的信件全部交给模型；每次请求模型之前，把这期间新到的信件接在工具结果后面一起交给模型（同 Claude Code：两次工具调用之间就能处理）；模型不再调用工具时这次运行结束，信箱里还有信件就接着跑下一次。
- 异步工具（后台 shell、`delegate_task(report_back)`）发起后立即返回；完成与运行中检查都只是往发起方的信箱里追加信件。

「一轮」不再是输入的单位，只剩「一次连续运行」的意思。

## 2. 已定的选择

1. **每一步保存**。一步 = 一次模型请求及其返回的工具调用全部执行完。这一步的消息、这一步交给模型的信件（记为已处理）在同一个事务里提交。失败或进程重启后从上一步继续：历史停在请求上就重发这次请求，停在带工具调用的回复上就执行这些调用（pydantic-ai 原生支持，已核实 2.57 `_agent_graph` 的续跑逻辑）。只有中断那一步里正在执行的工具会再执行一遍，已经保存的步骤不会重放。
2. **等提问**：会话停在 `ask_user` 上时消费者暂停，信件留在信箱里。回答到达时先作为提问的结果交回（`DeferredToolResults`），再接上信箱里排着的其他信件；用户发的普通消息算跳过（提问记为没回答）后同样处理；其他来源的信件（检查、完成通知）不唤醒消费者，等回答或跳过时一起交给模型。
3. **停止 = 消费停止，信箱清空，连带停下它发起的异步工作**：结束当前运行（已保存的步骤保留，正在执行、没出结果的工具调用补上「被停止」的结果），信箱里还没处理的信件标记为被丢弃（不删除，界面可见）；这个会话正在跑的后台任务一起结束（同 `job_kill`），它 `report_back` 委派出去、还在跑的 thread 一起停止（同样清空它们的信箱）。被停下的这些不再给这个会话投信（结局记为随会话停止），之后新到的信件照常唤醒消费者。
4. **推送**：每封信件带「用户是否在等它的回答」（用户的消息：是；触发器事件、运行中检查：否；后台任务完成：随发起它的那封信件）。一次运行结束时，处理过的信件里有一封用户在等，就把最后的回答推送给用户；否则不推（agent 可以自己 `notify_user`）。
5. **私有 thread**：同样是信箱。`ask_agent` 往子 thread 的信箱投信后，在发问方这一步里同步驱动子 thread 的消费者跑完，拿它的回答作为工具结果。

## 3. 数据

- **`mail` 表**（由 `session_events` 演化）：`id`、`session_id`、`kind`（user / answer / trigger / delegation / job / thread / check）、`content`、`attachments`（文件 id）、`answers`（answer 专用：tool_call_id → 结果）、`source`（如 `job:12`）、`awaited`（用户是否在等回答）、`report_to`（delegation 专用：结果交回的会话）、`created_at`、`state`（queued / consumed / discarded）、`consumed_by`（处理它的那一步的 run）。
- **运行**：仍是 `tasks` 表里的一条 task（kind `run`，lane 为会话），worker 领取后驱动消费者直到信箱空或停在提问上；payload 为空（输入都在信箱里）。失败按队列语义重试：重试就是从上一步续跑。界面上「失败了、点重试」针对 run。
- **消息**：`messages.task_id` 指向产生它的 run（压缩的「同一轮不拆开」改为同一 run 的同一步不拆开）。
- `TurnPayload`、turn 的 `prompt/attachments/answers/report_to` 字段、`session_events`、`dispatch_in` 的「已交给过一轮」推断全部删除。

## 4. 唤醒规则（唯一一处）

会话信箱里有 queued 信件、没有排队或运行中的 run、且（没有挂起的提问，或信件里有回答 / 用户消息）时，投递一个 run。调用方：投信时、run 结束时、定期对账（兜住投递事务失败与重启）。不再需要「已交给过」的推断：信件只有交给模型的那一步保存后才算处理，run 失败时信件仍是 queued，失败的 run 被重试或新信件到达时会再投递；最终失败的 run 不会因为同一批信件被无限重投——对账只在「没有 run 记录晚于最新信件」时投递（同现在的规则）。

## 5. 影响面

- 入口 `conversation.receive`：变为投信（新建会话或续写，续写规则不变）。用户消息、触发器、`delegate_task` 都经过它。
- `TurnRunner` → 消费者：`agent.iter()` 逐步驱动，每步提交；`before_model_request` 钩子取新信件并入请求。
- 提问：挂起判断不变（历史推导）；回答从 payload 移到 answer 信件。
- 停止：`stopped_messages` 的「补开头请求」不再需要（每步保存，开头请求已经在库里）。
- 后台任务、thread 交回、检查：`post_in` 变为投信（kind job / thread / check）。
- 压缩：运行之间压缩（run 结束且信箱空时），切点按步。
- 反思：按 run 计数。
- 界面：排队中的信件显示为待处理气泡（替代 open_turns 的 prompt）；被丢弃的信件显示为划掉；失败的 run 显示重试；实时事件按 run。

2. 消费者与逐步保存（核心，测试先行：续跑不重放已保存步骤、两次工具调用之间并入新信件、提问暂停与恢复、停止清空信箱）。
3. 入口、提问、停止、后台任务、交回改为投信。
4. 压缩、反思、界面。
